# Bug audit — `arm_custom_subset.circ`, 2026-10-24

One place for every known defect, after repair 3 (extra-transfer control) was
hand-wired and verified. Everything below was measured on the **real Logisim
5.0.0 engine** unless marked *structural* (derived from the file by the
`logisim/` toolkit, which has known geometry errors — see T2).

Supersedes the defect lists in `docs/CPU_DEFECTS.md` (2026-08-30) and
`CLAUDE.md` §8, which describe bugs that have since been fixed.

Circuit SHA-256 at time of audit: see `sha256sum arm_custom_subset.circ` in the
commit that adds this file.

## How it was checked

| method | what it is |
|---|---|
| Logisim regression suites | `register_offset_regression`, `memory_lane_regression`, `adversarial_regression`, `pre_multiply_audit --suite shifter/extra/deep` |
| differential testing | `tests/unicorn_diff.py`: random ARM programs run on the circuit **and** on Unicorn (ARM925T, an ARMv4T core); every register, NZCV and 1 KiB of RAM compared |
| directed matrices | every load/store type × addressing mode; every LDM/STM mode × writeback × list size |
| directed rule checks | where Unicorn is not canonical (unaligned access) or ARM is implementation-defined, expectations written by hand from the ARMv4T rules |
| block tests | `--test-vector` on `ks_32b`, `mul_32`, `csa_3to_2`, `partial_products` |
| structural | `logisim validate`, `tests/check_stage.py` on every stage |

The Unicorn model was itself checked: it rejects the ARMv5 `CLZ` (so it is a v4
model), and it is **not** canonical for unaligned word loads (byte read, not
rotate), so random tests only generate aligned accesses.

## A. CPU defects (the live datapath)

### D1 — `LDRH`/`LDRSB`/`LDRSH`/`LDM` overwrite NZCV  · **high** · spec ready

`cmp r0,#1` → `ldrh r2,[r10]` → the flags are now the ALU's, not the `cmp`'s.
`ldr`, `ldrb`, `str`, `strb`, `strh`, `stm` are correct.

*Cause* (`stage_EX`): `CPSR write = cond_pass AND NOT_DP AND s_bit`; the no-flag
list covers branch, BX and plain LDR/STR only. For halfword/signed and block
transfers bit 20 is **L**, read as **S**.

*Consequence*: a conditional `LDM` whose condition depends on a flag that its
own first cycle clobbers stops after one cycle (`ldmiami` with N=1 loads
nothing; `ldmiane`, `ldmiapl` work).

*Proof it is the only cause of the load/store differences*: 56/56 single forms
match; random load/store programs 0/8 with conditions, 8/8 without; with
conditions kept but the three loads removed, 10/10.

Fix: `specs/fix_7_flag_clobber.md` — 8 parts, 1 rewire, no new pins.

### D2 — unaligned word `LDR` is not rotated  · **low** · not specced

| `ldr r2,[r1,#k]`, word `0x11223344` at `r1` | hardware | ARMv4T |
|---|---|---|
| k = 1 | `11223344` | `44112233` |
| k = 2 | `11223344` | `33441122` |
| k = 3 | `11223344` | `22334411` |

ARMv4T loads the aligned word rotated right by `8 × addr[1:0]`. Compiled C
rarely does this, but hand-written code and some `memcpy` variants rely on it.
Unaligned `STR` is correct (low address bits ignored). Fix lives in
`stage_MEM`'s word-load data path: rotate by `addr[1:0] << 3`, word loads only.

### D3 — after an `LDM` that loads the PC, the next block transfer hangs  · **critical** · root cause not traced

| sequence | result |
|---|---|
| `ldmia r10,{r4,pc}` → `stmia r10,{r1}` | **never halts** |
| `ldmia r10,{pc}` → `stmia` | **never halts** |
| `ldmia r10,{r4,pc}` → `ldmia r10,{r5}` | **never halts** |
| `ldmia r10,{r4,pc}` → 3 × NOP → `stmia` | **never halts** |
| `ldmia r10,{r4,pc}` → `str` | ok |
| `ldmia r10,{r4}` → `stmia` | ok |
| `ldr pc,[r10]` → `stmia` | ok |

Realistic form: `bl f1` / `bl f2`, each `push {r4,lr}` … `pop {r4,pc}` —
**hangs**. One such call works; two leaf calls returning with `mov pc,lr` work.
Every non-leaf C function returns through `pop {…,pc}`, so compiled code with
two calls hangs.

*Hypothesis, not yet verified*: when the PC is the last register an `LDM`
loads, `block_transfer_control` never returns to idle (its done/active state is
skipped by the PC write), so the next transfer's `start` is never serviced and
`hold_pc` stays asserted. Next step: step it in Logisim and watch
`bt_active`, `bt_done` and `hold_pc` across the two transfers.

Why nothing caught it: the existing stack tests never do a second block
transfer after a `pop {…,pc}`; the differential `pc` category ends right after
the `LDM`.

### Verified correct (with D1 masked, see sweep table below)

* all 16 data-processing opcodes, every shifter form, carry/overflow rules
* all 14 condition codes; `B`, `BL`, conditional branches, loops
* every load/store: 8 types × 7 addressing modes (56/56)
* every block transfer: IA/IB/DA/DB × writeback × 5 list sizes (80/80)
* PC as an operand (+8) and every PC write this subset supports
* `LDRT`/`STRT`; reset state (all registers and NZCV zero); memory map
  (ROM readable from `0x0000`, RAM `0x1000`–`0x13FC`)

## B. Multiplier datapath (not yet integrated — matters for multiply)

### M1 — `ks_32b` drops bit 22 from the carry into bit 30  · **real** · 2 wires

3 of 1,996 vectors fail, all on `SUM30`. Signature: the carry into bit 30
behaves as if bit 22 always propagates (a generate at 22 is lost; a kill at 22
is ignored).

*Cause* (structural, consistent with the behaviour): **`pg_cell` @(1020,4300)**,
the level-3 prefix node for bit 29, takes `G_prev`/`P_Prev` from
**`pg_cell` @(1610,3660)** = G[26:23]. It must take them from
**`pg_cell` @(1800,3660)** = G[25:22] (next cell to the right, same row). The
span becomes [29:26]∘[26:23] — bit 26 twice, bit 22 never. All other 31
carry-ins trace to the correct span.

Discriminator: `A=0x3FC00000, B=0x00400000, Cin=0` → sum must be `0x40000000`.

### M2 — `mul_32` outputs the error value `E` for every input  · **real** · needs inspection

Even `0 × 0`. No width conflicts design-wide, so it is a driver/connection
problem. Its parts are fine on their own: `csa_3to_2` 45/45 (sum = X^Y^Z,
carry = majority<<1), `partial_products` 74/74.

*Structural observations — verify in Logisim before acting* (the toolkit's
subcircuit port geometry has been wrong before):

* the first CSA (label `un`, @940,370) has X, Y, Z undriven;
* each CSA appears to read the CSA **two** to its left, i.e. two interleaved
  chains rather than one;
* the second-to-last CSA (@7100,370) drives nothing; a wire ends 20 px from its
  `carry` port;
* partial product `p31` reaches no CSA.

A 32-row carry-save chain needs 30 CSAs fed in order (`p0,p1,p2`, then one per
`p3…p31`), each taking the previous CSA's sum/carry.

### M3 — ALU engine-mux inputs 2/3 not connected  · integration point

`ALU`'s engine mux `in3` has a wire ending 10 px off (structural). This is
where the multiplier result is meant to enter; it is part of the multiply
integration, not a regression.

## C. Behaviour of instructions that are not implemented

Not bugs in the subset, but they do things, and multiply work will change them.

| instruction | today | ARMv4T |
|---|---|---|
| `MUL` `MLA` `MULS` `UMULL` `SMULL` `UMLAL` `SMLAL` | **write garbage to Rd** (decoded as data-processing) | product |
| `SWP` `SWPB` | no effect | atomic swap |
| `MRS` `MSR` | no effect | CPSR access |
| `SWI` | no effect | SWI exception |
| undefined (`0xE7F000F0`) | **writes garbage to `r0`** | undefined exception |
| coprocessor (`MCR`) | **writes 0 to `r0`** | undefined exception |
| `BX` to an odd address (Thumb) | **not taken — falls through** (`NOT_THUMB` gate, deliberate) | switch to Thumb |

Long multiplies (`UMULL` family) are part of ARMv4T too; count them in the
multiply scope or list them as out of scope.

### Implementation-defined choices (allowed, worth documenting)

* `STR pc` and `STM {…,pc}` store **PC+8**. ARMv4 permits +8 or +12; the
  ARM7TDMI uses +12.

## E. Not tested — no claim either way

* `LDM`/`STM` with the base register in the list (ARM: unpredictable)
* `movs pc, lr` and other S-bit writes to the PC (privileged semantics)
* register-specified shifts with `Rs`/`Rm` = PC (ARM: unpredictable)
* long programs / compiled C against Unicorn (needs T5) — D3 shows why this
  matters: it only appears with two calls in sequence
* exhaustive operand values: the generator mixes boundary and random values;
  it samples, it does not enumerate
